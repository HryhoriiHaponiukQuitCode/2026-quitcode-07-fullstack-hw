# 0002. Ролі — у таблиці `profiles` з RLS через хелпер, а не в JWT; зміна ролі — функцією бази

- Статус: прийнято
- Дата: 2026-10-24
- AC: AC-ACCESS-01 (адміністратор змінює роль учасника), AC-ACCESS-03 (учасник не змінює роль сам собі),
  AC-ACCESS-04 (учасник не змінює роль іншому), AC-ACCESS-05 (не можна понизити останнього адміністратора)

## Контекст

- Матриця прав PM: роль змінює лише адміністратор; учасник роль не змінює нікому, зокрема собі; адміністратор може
  змінити роль і собі, але останнього адміністратора понизити не можна (рішення PM записане окремим рядком під
  матрицею). Учасник бачить і змінює лише власні бронювання; адміністратор бачить усі.
- Політики RLS мають знати роль того, хто робить запит. Публічний ключ лежить у бандлі, тож будь-хто з власною
  сесією може надіслати запит прямо в Data API. Перевірка лише в Server Action не захищає.
- Шаблон проєкту вже має `profiles.role`, хелпер `private.current_app_role()` (`security definer`,
  `set search_path = ''`) і `grant update (full_name)` — роль користувач не оновлює.
- Тести доступу — на PGlite (`asUser`), без Docker і без хмарного Auth.

## Рішення

- Роль лишається в `public.profiles.role`. Політики перевіряють `(select private.current_app_role())`.
- Зміна ролі — лише функцією `private.set_member_role(p_target, p_role)`: `security definer`, `set search_path = ''`.
  Першим рядком — перевірка, що викликає адміністратор. Захист останнього адміністратора — з `for update` на рядках
  адміністраторів. Виклик із застосунку — через обгортку `public.set_member_role` (`security invoker`), `execute`
  лише для `authenticated`.
- `grant update` на `profiles` лишається тільки на `full_name`: політика «оновлює власний рядок» не дає підвищити собі
  роль.
- Server Action `changeRole` — `getClaims()` і перевірка ролі для зрозумілої помилки, далі `supabase.rpc(…)` клієнтом
  користувача. Admin-клієнт (секретний ключ) тут не потрібен.

## Розглянуті варіанти

- **Роль у JWT через Custom Access Token Hook** (claim у токені, політики читають `auth.jwt()`). Ні: роль у токені
  застаріває до оновлення токена — понижений адміністратор ще якийсь час адміністратор. Потрібна окрема конфігурація
  хука в кожному проєкті Supabase, а на PGlite довелось би емулювати claims. Виграш у швидкості для нашого обсягу (до
  сотні користувачів) не потрібен.
- **Роль у `user_metadata`.** Ні, ніколи: користувач змінює `user_metadata` сам через `updateUser({ data })` з
  браузера.
- **Server Action з admin-клієнтом замість функції бази.** Ні: перевірку ролі довелося б тримати лише в коді. Тоді
  захист від прямого запиту тримається тільки на column grant, а «останнього адміністратора» без блокування рядків
  двоє адміністраторів можуть одночасно понизити один одного. До того ж секретний ключ потрапив би у Vercel без
  потреби в Admin API.

## Наслідки

- Простіше: зміна ролі діє з наступного запиту; правило прав живе в базі й однакове для сторінки, дії і прямого
  запиту; тести бази покривають усі відмовні AC.
- Складніше: кожна нова привілейована дія — функція в `private` з обгорткою в `public`; помилки бази (`FORBIDDEN`,
  `LAST_ADMIN`) Server Action перекладає в тексти AC.
- Якщо з'явиться роль «менеджер відділу» з правами на частину учасників — функція отримає перевірку відділу, а
  матриця PM — новий рядок; рішення лишається в силі.

## Як перевіряємо

- PGlite (`tests/db/access.test.ts`):
  - учасник не оновлює собі `role` ні оновленням профілю (`permission denied`), ні функцією (`FORBIDDEN`), а роль
    лишається `member` (AC-ACCESS-03);
  - останнього адміністратора не понизити (AC-ACCESS-05).
- Мутаційна перевірка в PR: тимчасовий `grant update (full_name, role)` і функція без першої перевірки → тести
  червоні (посилання на прогони в PR #12).
- `architecture.yml`, job «Секретний ключ лише на сервері»: admin-клієнт не з'явиться в Client Component, а ключ —
  поза `src/lib/supabase/admin.ts`.
